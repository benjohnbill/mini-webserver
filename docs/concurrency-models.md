# 웹서버 동시성 모델 비교

**백엔드 응답을 기다리는 요청이 네 개일 때, 다섯 번째 클라이언트가 작은 파일을 달라고 하면 언제 응답할 수 있을까?** 이 서버에서 워커 4개짜리 스레드 풀은 워커 하나가 빌 때까지 기다렸다. `fork`와 네 가지 이벤트 루프는 백엔드가 응답하기 전에 파일 전송을 끝냈다. 모든 모드가 같은 HTTP 파서와 정적 파일·echo·리버스 프록시 코드를 사용한다.

## 연결 하나가 기다리는 동안 누가 다음 연결을 맡는가

| 방식 | 연결을 수락한 다음 | 백엔드 응답이 늦어지면 |
|---|---|---|
| 멀티프로세스 `fork` | 부모가 연결마다 자식 프로세스를 하나 만든다. 자식이 요청을 처리하고 종료하면 부모가 `waitpid()`로 회수한다. | 해당 자식이 기다리는 동안 부모는 다음 연결을 받을 수 있다. 이 구현은 자식을 최대 64개까지 두며, 연결마다 프로세스 생성·회수 비용이 든다. |
| 멀티스레드 `pthread` | 메인 스레드가 연결 fd를 큐에 넣고, 미리 만든 워커 4개가 꺼낸다. 워커들은 같은 프로세스의 메모리를 공유하므로 큐를 변경할 때 뮤텍스를 잡는다. | 요청을 맡은 워커가 계속 그 연결을 담당한다. 4개가 모두 바쁘면 다음 연결은 최대 64칸의 대기 큐에 들어간다. |
| I/O 멀티플렉싱 | 한 스레드가 연결마다 현재 단계, 읽은 바이트 수, 아직 보내지 못한 데이터를 보관한다. 소켓이 준비되면 그 연결의 처리를 한 단계 진행한다. | 백엔드를 읽을 수 있을 때까지 해당 연결의 상태를 보관한다. 그사이 다른 클라이언트 소켓이 준비되면 같은 스레드가 그 요청을 처리한다. 이 구현은 최대 64개의 진행 중인 연결을 관리한다. |

예를 들어 `POST /echo`의 본문 5바이트 중 `he`만 도착했다고 하자. 이벤트 루프는 그 연결에 **2바이트 수신, 3바이트 남음**을 기록한다. 다음에 이 소켓을 읽을 수 있게 되면 이어서 받고, 다른 소켓이 먼저 준비되면 그쪽 일을 한다. 정적 파일은 8 KiB씩 동기적으로 읽으므로 디스크 읽기가 오래 걸리면 그동안 이벤트 루프도 기다린다. [연결별 상태와 요청 처리](../src/connection.c) · [프로세스와 스레드 풀 구현](../src/main.c)

### 이벤트 루프가 준비된 소켓을 찾는 네 가지 방법

| API | 서버가 커널에 전달하는 것 | 준비된 연결을 찾는 방법 |
|---|---|---|
| `select` | 매번 읽기·쓰기 fd 집합을 다시 구성해서 전달한다. | 반환된 집합을 검사한다. 이 구현에서 fd 번호는 `FD_SETSIZE`보다 작아야 한다. |
| `poll` | fd와 관심 이벤트를 담은 배열을 전달한다. | 반환된 배열을 훑으며 각 항목의 `revents`를 확인한다. |
| `epoll` · Linux | `epoll_ctl()`로 감시할 fd와 관심 이벤트를 커널에 등록하거나 변경한다. | `epoll_wait()`가 돌려준 준비된 이벤트 목록을 처리한다. |
| `kqueue` · macOS, FreeBSD | `kevent()`로 fd의 읽기·쓰기 필터를 등록하거나 변경한다. | `kevent()`가 돌려준 이벤트 목록을 처리한다. |

코드에서 `poll()`을 발견하면 **한 번에 어느 fd들을 기다리는지** 보면 모델을 구별할 수 있다. 스레드 풀의 워커는 자기가 맡은 연결에서 다음에 필요한 fd 하나를 기다린다. `-m poll`의 이벤트 루프는 리스닝 소켓과 여러 연결의 fd를 한 배열에 넣어 기다린다. [워커의 대기 코드](../src/connection.c) · [이벤트 루프의 대기 코드](../src/event_loop.c)

## 실험 1. 백엔드 요청 네 개와 정적 파일 요청 하나

1. 클라이언트 네 개가 각각 `GET /api/gate`를 보낸다. 테스트용 백엔드는 네 요청을 모두 받았다고 알리고 응답을 보류한다.
2. 다섯 번째 클라이언트가 `GET /`를 보낸다. 이 요청은 프록시가 로컬 파일에서 바로 응답할 수 있다.
3. 스레드 풀에서는 다섯 번째 요청이 250 ms 동안 대기 중인지 확인하고 백엔드 응답을 풀어 준다. 다른 모델에서는 백엔드를 계속 멈춰 둔 상태로 다섯 번째 요청이 2초 안에 `200`을 받는지 확인한다. 마지막으로 다섯 요청 모두 `200`을 받았는지 검사한다.

여섯 모드 모두 예상한 순서로 통과했다. 250 ms와 2초는 테스트의 판정 기준이다. 같은 실험에서 비교할 값은 **다섯 번째 응답이 백엔드를 풀기 전과 후 중 언제 완료됐는지**다. [실험 함수 `check_worker_capacity`](../tests/integration.py#L192)

Linux에서는 별도로 요청 두 개를 백엔드에서 기다리게 한 뒤 서버 프로세스를 관찰했다.

| 모드 | 부모 프로세스의 스레드 수 | 자식 프로세스 수 |
|---|---:|---:|
| `fork` | 1 | 2 |
| `pthread` | 5 (메인 1 + 워커 4) | 0 |
| `select`, `poll`, `epoll` | 1 | 0 |

이 상태에서 서버에 `SIGTERM`을 보내고 백엔드 응답을 풀자 각 모드는 진행 중이던 두 요청을 마친 뒤 종료했다.

## 실험 2. 작은 정적 파일의 처리량

2026-11-24에 macOS에서 ApacheBench로 로컬 서버의 `GET /`를 측정했다. 모드마다 동시 접속 16개로 300건씩 세 번 요청했다. 아래 값은 초당 요청 수의 중앙값이며 모든 실행에서 실패는 0건이었다.

| 모드 | 초당 요청 수 |
|---|---:|
| `fork` | 4,567 |
| `pthread` | 45,816 |
| `select` | 37,369 |
| `poll` | 40,225 |
| `kqueue` | 39,888 |

이 부하에서는 워커가 짧은 파일 요청을 끝내고 곧바로 다음 연결을 맡을 수 있었다. 앞 실험처럼 백엔드가 오래 기다리게 하면 워커를 점유하는 시간이 길어진다. 따라서 모델을 고를 때는 짧은 요청의 처리량과 느린 요청이 다른 연결에 미치는 영향을 함께 본다. Linux의 `epoll`은 기능 검사와 sanitizer 검사를 통과했고, 위 처리량 표는 같은 macOS 환경에서 측정한 값만 담았다.

## 재현 방법

`Week 13` 디렉터리에서 실행한다. `make test`는 임시 포트에서 서버와 백엔드를 직접 띄운다. macOS에서는 `kqueue`, Linux에서는 `epoll`을 포함해 OS별 5개 모드를 검사한다. 두 환경 모두 단위·통합 테스트와 AddressSanitizer·UndefinedBehaviorSanitizer 검사를 통과했다.

```sh
make test
make sanitize

# 다섯 번째 요청 실험을 포함한 통합 테스트를 한 모델에서만 실행
python3 tests/integration.py ./server poll
```

처리량을 재려면 첫 번째 터미널에서 측정할 모델로 서버를 켠다.

```sh
make
./server -m pthread 8080 ./public
```

두 번째 터미널에서 다음을 실행한다. 각 실행의 `Failed requests`와 `Requests per second`를 확인하고 초당 요청 수 세 개 중 가운데 값을 기록한다. 첫 번째 터미널에서 서버를 종료한 뒤 `-m` 값만 바꾸면 같은 조건으로 비교할 수 있다.

```sh
for trial in 1 2 3; do
    ab -s 5 -n 300 -c 16 http://127.0.0.1:8080/
done
```

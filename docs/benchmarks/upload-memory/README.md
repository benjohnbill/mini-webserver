# 업로드 백프레셔 적용 전후의 프록시 메모리

1 MiB 요청 64개를 동시에 업로드했을 때 프록시 프로세스의 최대 RSS가
69.73 MiB에서 5.48 MiB로 줄었다. 차이는 64.25 MiB로, 이전 구현이 연결마다
보관하던 요청 본문 약 1 MiB에 해당한다.

| 동시성 모델 | 동시 업로드 | 본문 크기 | 적용 전 최대 RSS | 적용 후 최대 RSS | 감소율 |
|---|---:|---:|---:|---:|---:|
| poll | 1 | 1 MiB | 2.55 MiB | 1.53 MiB | 39.9% |
| poll | 4 | 1 MiB | 5.81 MiB | 1.72 MiB | 70.4% |
| poll | 16 | 1 MiB | 18.53 MiB | 2.55 MiB | 86.3% |
| poll | 64 | 1 MiB | 69.73 MiB | 5.48 MiB | 92.1% |
| pthread | 4 | 1 MiB | 5.84 MiB | 1.84 MiB | 68.4% |
| poll | 64 | 4 KiB | 5.73 MiB | 5.48 MiB | 4.4% |

이전 구현은 요청의 `Content-Length`만큼 메모리를 할당하고 본문을 모두 받은 뒤 백엔드에 연결했다.
현재 구현은 요청 헤더를 받은 시점에 백엔드에 연결한다. 최대 8 KiB씩 읽고 보류된 바이트를
백엔드 소켓에 모두 쓴 뒤 다음 본문을 읽는다. 요청마다 헤더와 연결 상태를 저장하는 공간은
여전히 필요하다. 본문이 4 KiB일 때 64개 연결에서 절약한 메모리는 총 0.25 MiB였다.

## 측정 방법

- 2026-11-24, macOS 26.5.1 arm64, Apple Clang 21.0.0, `-O2` 빌드. 전후 빌드에는 같은 이벤트 루프와 동시성 설정을 사용했다. `poll`은 최대 64개 연결을 함께 처리하고, 기본 `pthread` 모드는 워커 4개를 사용한다.
- 로컬 TCP에서 백엔드 수신 버퍼를 32 KiB로 설정했다. 백엔드는 모든 업로드의 요청 헤더를 받을 때까지 기다리고, 250 ms 더 대기한 뒤 본문 읽기를 재개했다. 클라이언트는 918건 모두에서 HTTP 200과 백엔드가 계산한 본문의 SHA-256 일치를 확인했다.
- 조건마다 프록시를 새로 띄워 3회씩 측정했다. 두 번째 반복에서는 전후 실행 순서를 뒤집었다. 표는 각 프로세스의 수명 동안 운영체제가 기록한 최대 RSS(`wait4`의 `ru_maxrss`)의 중앙값이다. CSV에는 워밍업 직후와 백엔드 대기 중에 `ps`로 읽은 RSS도 함께 있다.
- RSS는 프록시 프로세스가 점유한 상주 메모리다. 커널 TCP 버퍼, 클라이언트와 백엔드의 메모리는 측정 범위 밖이다. [원시 측정값](results.csv)

## 재현

프로젝트 루트에서 실행한다. 패치는 현재 소스의 임시 복사본에서 업로드 경로를 본문 전체 수신 후 전달하는 방식으로 바꾼다. 캐시와 요청 제한은 양쪽 모두 끈다. 위 표는 2026-11-24에 기록한 값이다.

```sh
bench_dir=$(mktemp -d)
cp -R src Makefile "$bench_dir/"
patch -d "$bench_dir" -p1 < docs/benchmarks/upload-memory/before.patch
make -C "$bench_dir" server
make server
python3 tests/bench_proxy_memory.py "$bench_dir/server" ./server
```

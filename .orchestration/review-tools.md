# impl-tools 교차 리뷰

## 중요

1. **재로딩이 실패해도 `remove`가 백엔드를 종료합니다.** `scripts/lb.sh:33,228–229,239–245`
   - `save_members` 실패를 `add`와 `remove`가 모두 무시합니다. 예를 들어 `.lb/front.route.tmp`에 쓸 수 없으면 기존 route 파일이 그대로인데도 HUP을 보냅니다. `remove`는 상태 반영 대기가 만료되거나 HUP 전송이 실패해도 `stop`을 실행하므로, front가 아직 선택하는 백엔드를 끕니다. 멤버 파일은 이미 갱신됐을 수 있어 같은 `remove`를 재시도하기도 어렵습니다.
   - 파일 갱신 실패를 즉시 처리하고, 새 목록 적용을 확인한 뒤에만 종료하세요. 실패 시 실행 중인 백엔드를 유지하고 멤버 변경을 재시도할 수 있게 하세요.

2. **업데이트 직후 첫 명령이 `remove`면 옛 front가 내려간 채로 남을 수 있습니다.** `scripts/lb.sh:69–70,120–122,193–205,261–263`
   - 프로젝트 소스와 스크립트만 갱신된 상태에서 `mini-web backend rm bN`을 실행하면 `remove` 경로는 빌드를 하지 않습니다. 인라인으로 실행 중인 옛 front는 안전장치에 따라 HUP을 피하지만, `refront`가 이를 먼저 종료한 뒤 옛 디스크 바이너리로 `=@.lb/front.route`를 전달합니다. 옛 바이너리는 이 옵션을 파싱하지 못해 기동에 실패합니다.
   - 재시작 분기에 진입할 때 기존 front를 정지하기 전에 빌드 성공을 확인하세요.

3. **목록 교체를 확인하자마자 느린 백엔드를 종료해 이미 시작한 요청을 끊습니다.** `scripts/lb.sh:136–142,239–244,267–269`, `tools/slow_backend.py:27–37,44–49`
   - `lb.sh slow b2 900`으로 b2를 바꾸고 요청이 b2에서 응답을 기다리는 동안 `remove b2`를 실행하면, status에서 b2가 빠진 직후 `SIGTERM`을 보냅니다. 느린 서버의 TERM 핸들러는 즉시 프로세스를 종료하므로 아직 응답하지 않은 요청이 끊길 수 있습니다. status에서 빠졌다는 것은 새 테이블이 적용됐다는 뜻이며, 이전 테이블을 잡은 요청은 계속 진행할 수 있습니다.
   - 제거 대상이 진행 중인 요청을 마칠 수 있게 종료 절차를 보완하고, 느린 응답을 기다리는 클라이언트가 제거 후에도 정상 응답을 받는지 확인하세요.

4. **부하 테스트는 부하 중 성공한 재로딩이 0회여도 통과합니다.** `scripts/functional_test.sh:235,249–263`
   - `N`은 HUP 전송 시도마다 증가합니다. 부하 구간에서 재로딩이 전부 거부되거나 지연되어도 기존 목록으로 6,000개 응답이 성공하면 검사를 통과합니다. 이어지는 `hup_rows`는 부하가 끝난 뒤에만 목록을 확인합니다.
   - 부하 시작을 확인한 뒤 목록을 바꾸고, 부하 프로세스가 끝나기 전에 새 `reload: ok`와 달라진 목록을 최소 한 번 확인하세요.

## 사소

5. **반영 대기가 스크립트의 약 2초 제한과 테스트의 1초 판정을 초과할 수 있습니다.** `scripts/lb.sh:207–215`, `scripts/functional_test.sh:225,229–233`
   - 스크립트의 20회 반복은 100ms 대기 외에 매회 최대 500ms 요청을 기다립니다. 기능 테스트도 매회 최대 1초 요청 뒤 100ms를 쉽니다. 예를 들어 테스트의 첫 상태 요청이 950ms 뒤 옛 목록을 반환하고 두 번째 요청이 새 목록을 읽으면 1초를 넘겨도 통과합니다.
   - 전체 마감 시각을 한 번 정하고 각 상태 요청과 대기의 시간을 남은 시간으로 제한하세요.

6. **파일 삭제 테스트는 해당 HUP가 처리되지 않아도 통과합니다.** `scripts/functional_test.sh:265–277`
   - 직전 세 잘못된 파일은 각각 실패 로그 증가를 검사합니다. 파일 삭제에서는 300ms만 기다린 뒤 그대로인 목록과 카운터를 확인하므로, 삭제 때 보낸 HUP를 무시해도 해당 검사가 통과합니다. 마지막 grep은 앞의 세 실패 로그가 있어 성공합니다.
   - 파일 삭제에도 동일하게 실패 로그 증가를 기다린 뒤 기존 목록을 검사하세요.

7. **`mini-web`의 정상 출력에서 front 포트와 종류 필드가 빠졌습니다.** `scripts/mini-web:8–12`, `scripts/lb.sh:129–130,207–212`
   - `mini-web backend new/rm`은 `lb.sh` 출력을 그대로 전달합니다. 기존의 `front started (pid N, :8080, webserver)` 행이 `front reloaded (pid N)`로 바뀌면서, 동작을 나타내는 동사 외에 포트와 종류도 사라졌습니다.
   - 재로딩 메시지에서 기존 행의 필드를 유지하세요.

정적 검토만 했습니다. Docker, 기능 테스트, 데모는 실행하지 않았습니다.
